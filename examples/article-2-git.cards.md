# 知识卡片：Git 分支管理

共 6 张卡片，覆盖：分支的本质、功能分支模型、合并方式、冲突处理、合并保护措施、rebase 与 merge 取舍。

### 卡片 1：分支是轻量级指针
**核心知识**：Git 分支本质上是一个指向某个提交（commit）的轻量级指针。
**简明解释**：创建和切换分支只是移动或新建指针，几乎不复制文件，所以成本极低。
**例子 / 自测**：为什么在 Git 里随手建一个分支几乎不用犹豫？

### 卡片 2：功能分支模型
**核心知识**：功能分支模型让 main 保持稳定，新功能或修复在独立分支开发，完成后合并回 main。
**简明解释**：主干始终可用，开发在旁路进行，最后通过合并请求（pull request）或 git merge 收口。
**例子 / 自测**：为什么不要把未经测试的代码直接提交到 main？

### 卡片 3：快进合并与三方合并
**核心知识**：fast-forward 在目标分支无新提交时直接移动指针；three-way merge 在两边都有新提交时创建新的合并提交。
**简明解释**：一条路直走就"快进"，分叉了就"三方合并"把两条历史并到一起。
**例子 / 自测**：什么情况下 Git 会创建合并提交而不是直接快进？

### 卡片 4：冲突的产生与解决
**核心知识**：两个分支改了同一文件的同一部分时产生冲突，需手动编辑保留想要的改动，再 git add 标记为已解决并提交。
**简明解释**：Git 不知道两处修改该留哪个，只能由人来裁决。
**例子 / 自测**：解决冲突后，还需要做什么操作才算完成？

### 卡片 5：合并前的保护措施
**核心知识**：为保护 main，团队常要求合并前通过自动化测试、至少一名成员代码审查，并保持提交历史清晰。
**简明解释**：用测试和 review 两道闸门，降低坏代码进入主干的概率。
**例子 / 自测**：一个 PR 要合入 main，通常至少要满足哪两个条件？

### 卡片 6：rebase 与 merge 的取舍
**核心知识**：rebase 让历史线性干净但会改写提交历史，不适合已公开分享的分支；merge 保留完整历史但可能产生较多合并提交。
**简明解释**：rebase 好看但有风险，merge 安全但较杂乱，各有适用场景。
**例子 / 自测**：为什么已经推送到远端共享的分支，不要随便 rebase？
